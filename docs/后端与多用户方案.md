## 一、当前架构：没有后端，也没有"用户"

```
浏览器 ──> 静态文件（GitHub Pages）
   │
   └──> 数据全部存在这台设备的 localStorage 里
        （键名 kivotos-kaoyan-v1）
```

**"不同用户"是怎么区分的？答案是：靠浏览器，不靠账号。**

| 场景 | 结果 |
|------|------|
| 你用自己的手机打开 | 看到你自己手机上的数据 |
| 你用自己的电脑打开 | 看到你自己电脑上的数据（和手机是**两份独立数据**） |
| 同学用他的手机打开同一个网址 | 看到的是**他自己的空数据**，看不到你的任何东西 |
| 你把网址发给朋友 | 他能用，但他的数据和你完全隔离 |

**为什么这样是安全的**：`localStorage` 是浏览器按「站点」隔离的沙箱。任何一个访客打开你的网址，
拿到的都是一份全新的空白数据，你的备考记录**从来没有上传到任何服务器**——因为根本没有服务器。
GitHub Pages 只负责把静态文件发出去，它对每个访客发的都是同样几个文件。

**代价**：没有账号，所以**换设备不会自动同步**。数据跟着浏览器走，清了缓存就没了。

## 二、三条升级路径（按需要选，不用一步到位）

### 路径 0：什么都不做（推荐给现在的你）

**适合**：一个人用，主要在 1–2 台设备上。

- 换设备/换浏览器：设置 → 数据与迁移 → **导出备份**（下载一个 JSON 文件）→ 在新设备**导入**
- 手机上用微信/QQ 把 JSON 文件传给自己就行，30 秒的事

**优点**：零成本、零维护、零隐私风险、断网可用。
**缺点**：手动，且必须记得定期备份。

> 页面里「设置 → 跨设备同步」就是给这条路径做的：可以复制文本直接粘贴过去。

### 路径 1：用 GitHub Gist 做云同步（真正的跨设备，仍然没有后端）

**适合**：想在多台设备间自动同步，但不想自己运维服务器。

**原理**：GitHub 的 Gist 是一个「可以当小型数据库用的文件存储」。
用户建一个**私密 Gist** 存自己的数据 JSON，网站用 GitHub API 读写它。

```
浏览器 ──> GitHub API（带用户自己的 token）──> 私密 Gist（用户的云端数据）
```

**怎么区分用户**：每个用户用**自己的 GitHub token + 自己的 Gist**，
互不相干。你的服务器上依然什么都没有。

**实现要点**（约 100 行代码）：

```js
// src/lib/gist-sync.js
const GIST_API = 'https://api.github.com/gists'

// 1. 保存：把整个 state 写进用户的私密 Gist
export async function pushToGist({ token, gistId, data }) {
  const filename = 'kivotos-kaoyan.json'
  const body = {
    description: '基沃托斯作战本部 · 考研数据备份',
    files: { [filename]: { content: JSON.stringify(data, null, 2) } }
  }
  const url = gistId ? `${GIST_API}/${gistId}` : GIST_API
  const res = await fetch(url, {
    method: gistId ? 'PATCH' : 'POST',
    headers: {
      Authorization: `Bearer ${token}`,
      Accept: 'application/vnd.github+json',
      'Content-Type': 'application/json'
    },
    body: JSON.stringify(body)
  })
  if (!res.ok) throw new Error(`GitHub 返回 ${res.status}`)
  const json = await res.json()
  return json.id // 首次创建后把 id 存下来，之后都用它
}

// 2. 拉取
export async function pullFromGist({ token, gistId }) {
  const res = await fetch(`${GIST_API}/${gistId}`, {
    headers: { Authorization: `Bearer ${token}`, Accept: 'application/vnd.github+json' }
  })
  if (!res.ok) throw new Error(`GitHub 返回 ${res.status}`)
  const json = await res.json()
  const file = Object.values(json.files)[0]
  return JSON.parse(file.content)
}

// 3. 合并策略：按 updatedAt 取新的那份，或按 id 并集合并
export function mergeByUpdatedAt(local, remote) {
  return (remote.updatedAt || 0) > (local.updatedAt || 0) ? remote : local
}
```

**需要在设置里加 3 个输入框**：GitHub token（勾 `gist` 权限）、Gist ID、一个「立即同步」按钮。

**优缺点**：
- ✅ 仍然零服务器、零费用
- ✅ 数据在用户自己的私有 Gist 里，你作为站主看不到
- ❌ 用户要自己申请 token，对小白有门槛
- ❌ 有冲突合并问题（两台设备同时改会打架，需要定合并规则）

### 路径 2：真正的后端（Supabase，推荐）✅ 已实现

> **实现情况**：这条路径已经落地。代码在 `src/lib/cloud.js`（约 700 行，含中文注释）、
> 建表脚本在 `docs/supabase-schema.sql`、界面在「设置 → 云端同步」、测试在
> `scripts/test-cloud.mjs`（49 项，自带假 Supabase，会真的拦越权写入）与
> `scripts/test-cloud-live.mjs`（打真项目）。
>
> 实际实现比下面的草案多了几件事，都是踩过坑之后加的：
> - **冲突处理**：两台设备都改过时不自动覆盖，弹窗让用户选，并把两边的数据摘要摆出来
> - **空数据保护**：本机是空的时候不准往云端推，否则会把备份用空白覆盖掉
> - **残留清理**：换过项目地址时，清掉旧项目留下的会话，避免「怎么都登不上」
> - **错误中文化**：把 PostgREST / GoTrue 的英文报错翻译成「表没建 / 密码不对 / 邮件发太频繁」
> - **对话单例**：会话按身份缓存，避免「重绘 → 订阅认证事件 → 重绘」的自激循环

**适合**：想让**多个人各自注册使用**，或者你自己想要「登录后到处都能用」。

**为什么推荐 Supabase 而不是自己写 Node 服务**：

| 对比项 | Supabase | 自己写 Node + SQLite |
|--------|----------|----------------------|
| 免费额度 | 500MB 数据库 + 5万月活，够用 | 要自己找免费主机 |
| 认证 | 内置邮箱/魔法链接/OAuth | 要自己实现注册登录、密码加密、找回密码 |
| 权限 | **行级安全（RLS）**，SQL 层面保证用户只能碰自己的数据 | 要自己写每个接口的鉴权，写漏一个就泄露 |
| 运维 | 托管，不用管备份扩容 | 要管进程、备份、HTTPS、域名 |
| 代码量 | 前端直接用 SDK，约 150 行 | 前后端加起来 800 行起 |

**数据模型**：

```sql
-- 一张表就够，每个用户一行，整份数据放 JSONB
create table kaoyan_data (
  user_id    uuid primary key references auth.users(id) on delete cascade,
  payload    jsonb not null default '{}'::jsonb,
  updated_at timestamptz not null default now()
);

-- 关键：开启行级安全，用户只能读写自己那一行
alter table kaoyan_data enable row level security;

create policy "只能读自己的" on kaoyan_data
  for select using (auth.uid() = user_id);

create policy "只能写自己的" on kaoyan_data
  for insert with check (auth.uid() = user_id);

create policy "只能改自己的" on kaoyan_data
  for update using (auth.uid() = user_id) with check (auth.uid() = user_id);
```

**「如何识别不同用户」的答案就在这里**：

1. 用户在网页上输入邮箱 → Supabase 发一封**魔法链接**邮件（不用记密码）
2. 点链接回来，Supabase 给浏览器一个 **JWT**，里面带着 `user_id`（UUID）
3. 之后每次读写数据库都带这个 JWT
4. **`auth.uid()` 就是当前用户的 UUID**，RLS 策略把它和 `user_id` 比对——
   即使有人改了前端的 JS 想查别人的数据，**数据库这一层也会拒绝**，这是关键。

**前端只需要这几个函数**：

```js
// src/lib/cloud.js
import { createClient } from '@supabase/supabase-js'
const sb = createClient(SUPABASE_URL, SUPABASE_ANON_KEY) // anon key 是公开的，安全靠 RLS

export async function signInWithEmail(email) {
  const { error } = await sb.auth.signInWithOtp({
    email,
    options: { emailRedirectTo: location.origin + location.pathname }
  })
  if (error) throw error
}

export async function currentUser() {
  const { data } = await sb.auth.getUser()
  return data.user // null 表示没登录
}

export async function saveCloud(payload) {
  const user = await currentUser()
  if (!user) throw new Error('未登录')
  const { error } = await sb.from('kaoyan_data').upsert({
    user_id: user.id,           // 由数据库策略兜底校验，伪造也没用
    payload,
    updated_at: new Date().toISOString()
  })
  if (error) throw error
}

export async function loadCloud() {
  const user = await currentUser()
  if (!user) return null
  const { data, error } = await sb.from('kaoyan_data').select('payload').eq('user_id', user.id).maybeSingle()
  if (error) throw error
  return data?.payload ?? null
}
```

**注意 `SUPABASE_ANON_KEY` 可以直接写在前端**——它是设计成公开的，
真正的安全边界是数据库的 RLS 策略，不是这个 key。

**优缺点**：
- ✅ 多用户互不干扰，且是数据库层强保证
- ✅ 换设备登录就能用，数据自动同步
- ✅ 免费额度对个人/小圈子足够
- ❌ 引入了外部依赖，网站不再"纯静态"，离线不可用
- ❌ 需要注册 Supabase 账号、建表、配认证，约 1 小时工作量

## 三、给你的具体建议

**如果只是你一个人用**：留在路径 0。最大的实际风险不是"没有云同步"，
而是**"哪天清了浏览器数据，几个月的记录没了"**——所以每周日花 30 秒导出一份备份 JSON，
存到网盘或微信收藏，比什么方案都便宜。

**想要「换设备自动同步」或「给同学各自使用」**：直接用已经做好的路径 2（Supabase）。
`schema` 已经开好行级安全，代码和测试都在仓库里，10 分钟能把项目建起来。

**不要做的事**：
- ❌ 不要为了同步去自己写 Node 服务 —— 你会同时背上服务器、证书、备份、鉴权的运维成本，
  而这些 Supabase 都免费帮你做了
- ❌ 不要把所有人的数据存在你服务器的同一个文件里 —— 那是给自己造一个隐私事故
- ❌ 不要把 `service_role` key 放进前端 —— 那等于把数据库的钥匙交出去。本站用它做安全边界的是
  RLS，前端的 `anon key` 本来就是公开的
